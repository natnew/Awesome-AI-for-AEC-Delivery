# Contributing

Thanks for helping improve **Awesome AI for AEC Delivery**. This is a curated list, so quality, relevance and trust matter more than volume.

All content lives in a single file: [`README.md`](README.md). There is no build step.

## What Belongs Here

A resource should help architects, engineers or builders apply AI across the AEC lifecycle. It must be:

- **Relevant:** built for AEC, or a general AI tool that is widely used in AEC workflows.
- **Maintained:** recent releases or commits, working links, real documentation.
- **Available today:** no marketing pages for products that are not yet usable, and no vapourware.
- **Useful:** it adds something the list does not already cover.

AEC is physical and safety-critical, so resources that support traceability, verification and professional accountability are especially welcome.

## How to Add a Resource

1. **Fork** the repository and create a branch, for example `add-<resource-name>`.
2. **Search `README.md`** first to confirm the resource is not already listed.
3. **Pick the most specific section** of the taxonomy (see [How This List Is Organised](README.md#how-this-list-is-organised)). Do not add to a broad section if a narrower one fits.
4. **Add one entry** using this format:

   ```markdown
   - 🟢 [Name](https://example.com) - Short description ending with a full stop.
   ```

   Legend icons: 🟢 open source · 💼 commercial · 📄 paper · 📊 dataset · 🎓 learning resource. Match the icon placement used by neighbouring entries.
5. **Update the Contents** table if you add a new heading.
6. **Open a pull request** with a clear title, such as `Add <Name> to <Section>`.

## Entry Style

- One resource per pull request.
- Describe what the resource *does*, in a neutral tone. No hype, superlatives or "best".
- Keep descriptions to one sentence and end with a full stop.
- Use the official project or paper URL, not a tracking or shortened link.
- Keep alphabetical or existing ordering within a section, whichever the section already uses.
- Use British or American spelling consistently with the surrounding text; do not mix them within an entry.

## Pull Request Checklist

- [ ] The resource is in the most specific section.
- [ ] The link works and points to the canonical source.
- [ ] The entry follows the format and ends with a full stop.
- [ ] The resource is maintained and available today.
- [ ] I have **disclosed any affiliation** with the resource.
- [ ] If I added a new category, I explained where it fits in the five-layer taxonomy.

## Proposing Structural Changes

For new categories, reorganisation or edits to the BIM Primer, open an issue first so the change can be discussed before you invest time. Corrections to factual errors or broken links can go straight to a pull request.

## Reporting Problems

Open an issue for dead links, outdated entries, or resources that no longer meet the criteria above. Include the section and a link to the evidence.

## Code of Conduct

Be respectful and constructive. Assume good faith, review the content rather than the contributor, and keep discussion on topic.
